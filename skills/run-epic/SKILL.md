# Run Epic

Autonomous epic orchestrator. Fans out per-ticket pipeline agents in parallel, manages dependencies, batches BLOCK escalations into single human interruptions, and resumes cleanly from a state file on restart. The orchestrator makes the easy calls autonomously and escalates only when a decision requires human accountability.

The only human stops are the batched BLOCK escalation and the final PR review. No mid-pipeline stops.

## Step 0 — Parse arguments

Parse `$ARGUMENTS` for:
- Positional epic ID (GitHub issue number or ADO work item ID)
- `--tickets <n1,n2,n3>` — explicit comma-separated ticket list
- `--project <path>` — absolute path, or alias key from `~/.claude/project-aliases.json` (see README)
- `--max-parallel N` — default 4
- `--base <branch>`

Exactly one of the positional epic ID or `--tickets` is required. If neither is present, ask which to use and stop until answered.

## Step 1 — Resolve project

If `--project` is given: treat it as an absolute path. If it matches a key in `~/.claude/project-aliases.json`, resolve through the alias map. If `--project` is omitted: check cwd for a `CLAUDE.md`; if absent, ask for the project path and stop until answered. Set `PROJECT_DIR` to the resolved path.

Detect the provider: run `git -C $PROJECT_DIR remote get-url origin`. A URL containing `dev.azure.com` or `visualstudio.com` is ADO; a URL containing `github.com` is GitHub.

Resolve the base branch. If `--base` is given, use it. Otherwise set `BASE_BRANCH` to the repo default branch (`git -C $PROJECT_DIR remote show origin | grep 'HEAD branch'`).

Derive `PROJECT_NAME` from the remote URL: strip the path prefix and the trailing `.git`.

## Step 2 — State file paths

Set:
```
STATE_DIR = ~/.claude/history/<PROJECT_NAME>
MASTER_FILE = $STATE_DIR/pipeline-state.json
```

Ensure the directory exists: `mkdir -p $STATE_DIR`.

## Step 3 — Re-entry check

If MASTER_FILE exists:

- If master `status` is `paused-awaiting-human`: re-surface the pending escalation from `pendingEscalation`. Do not resume dispatching. Wait for the user to resolve.
- For each per-ticket sidecar:
  - `pr-ready`, `blocked`, or `crashed` — report status only, take no action.
  - `queued` with all `DEPENDENCY_MAP[id]` entries in `pr-ready` or `blocked` — dispatch (Step 7, then Step 8).
  - Mid-pipeline (`grill` through `verify`) — check `agentSessionId`. If the session is alive, do nothing, the agent is still running. If the session is dead, set sidecar `stage = "crashed"`, record `crashedAt`, `crashStage`, `crashDetail`, and add to the escalation batch.
- Continue to the dispatch loop (Step 8).

If MASTER_FILE does not exist: continue to Step 4.

## Step 4 — Fetch tickets

GitHub: run `gh issue view $EPIC_ID` to fetch the epic, then list child issues referenced in its body. ADO: run `az boards work-item show --id $EPIC_ID` to fetch the epic, then fetch children via its relations.

If `--tickets` is given: fetch each ticket directly rather than from an epic parent.

For each ticket, extract: `id`, `title`, `body`, `ac`, `url`. Extract `ac` by scanning the body for a `## Acceptance Criteria` or `## AC` section or checkbox lists; if none is found, fall back to the full body.

## Step 5 — Pass-1 dependency scan and cycle detection

Scan all ticket bodies for:
- Explicit sequencing language ("depends on #N", "after #N ships", "blocked by #N")
- Shared named entities — tables, components, routes, or migration files mentioned in 2 or more tickets
- Shared ordering labels

Build `DEPENDENCY_MAP[id] = [prerequisite ids]`.

Run DFS cycle detection over `DEPENDENCY_MAP`. On any cycle: stop. Present the offending ticket chain as a hard BLOCK. Do not write state and do not dispatch until the ordering is resolved.

## Step 5b — Epic-level best practice research

Scan all ticket bodies and the epic body for decision-bearing topics — library choices, architectural patterns, data modeling decisions, query strategies, auth approaches, or any phrase implying a choice between competing approaches. De-duplicate topics that appear across multiple tickets.

For each distinct topic (max 6 — prioritize topics that appear in 2 or more tickets, then highest-stakes singles), invoke `/best-practice <topic> --project <PROJECT_DIR>`. Run these invocations sequentially.

Collect all finding blocks and write them to `$PROJECT_DIR/BEST_PRACTICES.md`, prefaced with:

```
# Best Practice Findings
Generated by /best-practice during epic <EPIC_ID>
```

If no decision-bearing topics are found across any ticket, skip this stage and do not create the file.

`BEST_PRACTICES.md` is written to the project root once here so all per-ticket `/run-ticket` invocations in Step 9 inherit it automatically — per-ticket Best Practice stages will find the file and skip re-research for topics already covered.

## Step 6 — Write initial state

Write MASTER_FILE atomically (write to `$MASTER_FILE.tmp`, then `mv $MASTER_FILE.tmp $MASTER_FILE`):
```json
{
  "epic": "<EPIC_ID or ticket list>",
  "project": "<PROJECT_NAME>",
  "projectDir": "<PROJECT_DIR>",
  "base": "<BASE_BRANCH>",
  "maxParallel": N,
  "created": "<ISO>",
  "updated": "<ISO>",
  "orchestratorVersion": 1,
  "status": "running",
  "pendingEscalation": null,
  "dependencyMap": {}
}
```
Set `dependencyMap` to `DEPENDENCY_MAP`.

Write each per-ticket sidecar `$STATE_DIR/pipeline-state-<id>.json` atomically (`.tmp` → `mv`):
```json
{
  "id": "42",
  "stage": "queued",
  "verdict": null,
  "reviseCounts": { "critic-0": 0, "critic-1": 0, "critic-2": 0 },
  "branch": null,
  "worktree": null,
  "pr": null,
  "blocks": [],
  "crashedAt": null,
  "crashStage": null,
  "crashDetail": null,
  "stageStartedAt": null,
  "stageCompletedAt": null,
  "agentSessionId": null
}
```

## Step 7 — Ticket setup (before dispatch)

For each ticket being dispatched:

Generate the branch name `<id>-<slugified-title>` — lowercase, hyphen-separated, max 60 characters.

Create the branch:
```
git -C $PROJECT_DIR fetch origin $BASE_BRANCH
git -C $PROJECT_DIR checkout -b <BRANCH> origin/$BASE_BRANCH
git -C $PROJECT_DIR push -u origin <BRANCH>
git -C $PROJECT_DIR checkout $BASE_BRANCH
```

Assign and record the ticket. GitHub: `gh issue develop <ID> --name <BRANCH>`. ADO: add a comment on the work item with the branch name.

Update the sidecar `branch` field atomically (`.tmp` → `mv`).

## Step 8 — Dispatch loop

Poll every 30 seconds.

**8a** — Read all sidecars into a live view.

**8b** — Count tickets in `implement`, `polish`, or `verify`. If the count is at or above MAX_PARALLEL, skip 8c this cycle.

**8c** — For each `queued` ticket where all `DEPENDENCY_MAP[id]` entries are in `pr-ready` or `blocked`: set sidecar `stage = "implement-pending"`, `stageStartedAt = now` (atomic, `.tmp` → `mv`). Run the pass-2 conflict check (8f). If the ticket overlaps an in-flight ticket, hold it at `implement-pending`. Otherwise dispatch the pipeline agent (Step 9), then set sidecar `stage = "grill"` and `agentSessionId` (atomic, `.tmp` → `mv`).

**8d** — Detect BLOCK transitions. Any sidecar that newly entered `blocked` this cycle is added to the escalation batch.

**8e** — Detect crashes. For any mid-pipeline ticket with a confirmed dead session: set sidecar `stage = "crashed"`, `crashedAt = now`, `crashStage = <prior stage>`, `crashDetail = "session terminated"` (atomic, `.tmp` → `mv`), and add to the escalation batch. For any mid-pipeline ticket active more than 60 minutes without a stage transition: alert the user. Do not crash it. After the alert fires, check that ticket's session liveness every 5 minutes — independently of the 30-second dispatch cycle — until either a stage transition is detected or the session is confirmed dead.

**8f** — Pass-2 conflict check, run after a ticket's implement stage completes. For each in-flight ticket run `git -C $PROJECT_DIR diff --name-only origin/$BASE_BRANCH...<BRANCH>`. Cross-reference the file lists. Any `queued` or `implement-pending` ticket that shares files with an in-flight ticket between `implement` and `pr-ready` holds at `implement-pending` until the overlap clears.

**8g** — Check BLOCK escalation. If the escalation batch is non-empty AND either no tickets remain in an active stage OR 30 minutes have elapsed since the first BLOCK in the batch: proceed to Step 10.

**8h** — If every ticket is in `pr-ready`, `blocked`, or `crashed`: proceed to Step 11.

## Step 9 — Pipeline agent dispatch

Dispatch each pipeline agent as a `claude` subagent with `isolation: "worktree"` and `model: "opus"`. Pass this prompt, with all slots filled:

> Invoke `/run-ticket` with the following arguments:
>
> ```
> /run-ticket {{TICKET_ID}} --project {{PROJECT_DIR}} --base {{BASE_BRANCH}} --branch {{BRANCH}} --sidecar {{SIDECAR_PATH}}
> ```
>
> `--branch` is pre-created — do not create a new one. `--sidecar` enables state tracking for the orchestrator — write all stage updates to it atomically. The master state file at `{{MASTER_FILE}}` is read-only: poll it during the implement-pending gate but never write to it.
>
> Report back when `/run-ticket` completes or returns a BLOCK.

## Step 10 — BLOCK escalation

Present all blocked tickets to the user in a single message. For each blocked ticket include:
- Ticket number and title
- Which critic blocked it, and whether the REVISE cap was the reason
- The full Skye output
- The blocked artifact: the proposal for critic-0 or critic-1 blocks, a diff summary for critic-2 blocks

Write master atomically (`.tmp` → `mv`): `status = "paused-awaiting-human"`, `pendingEscalation = { "tickets": [...], "raisedAt": now, "resolvedAt": null }`.

Stop dispatching. Wait for the user to resolve in the current session.

Resolution options per ticket:
- **Proceed (override)** — require a written rationale. Store it in the sidecar `blocks` field alongside Skye's original output. Resume the ticket from its blocked stage.
- **Revise manually** — provide new direction. Reset the ticket to `propose` for critic-1 or critic-2 blocks, or to `grill` for critic-0 blocks. Re-dispatch.
- **Drop** — write sidecar `stage = "blocked"` permanently.

<!-- Session history save point after BLOCK escalation resolution. See README. -->

After resolution: write master atomically `pendingEscalation.resolvedAt = now`, `status = "running"`. Resume the dispatch loop (Step 8).

## Step 11 — Completion

Write master atomically (`.tmp` → `mv`): `status = "complete"`, `updated = now`.

Surface to the user:
- **PRs ready for review** — a table of ticket number, title, branch, PR URL
- **Blocked tickets** — a table of ticket number, title, blocking reason
- **Crashed tickets** — a table of ticket number, title, crash stage
- **Total wall time** — elapsed since master `created`
